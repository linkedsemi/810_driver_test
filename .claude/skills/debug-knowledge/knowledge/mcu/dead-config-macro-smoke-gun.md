# "定义了但从未被引用"的配置宏 = 漏初始化的烟雾枪

## 现象

某通信用例恒失败：一侧返回 `-ETIMEDOUT`，另一侧返回 **`0`（成功）**，状态量也为 0。
按"接线错 / 没选片 / 对端不在位"排查会一轮轮白跑。

## 根因

源文件里为这次通信准备的一组配置宏（`LB_FREQ_HZ` / `LB_OP_M` / `LB_OP_S` 之类）
**只出现在 `#define` 行，从未被任何代码引用**；真正传给驱动的 `struct <bus>_config`
是**全零**的静态对象：

- 主机侧：字长字段为 0 → 控制器状态机不推进 → `-ETIMEDOUT`；
- 从机侧：`operation` 少了 `SPI_OP_MODE_SLAVE` 位 → 驱动走"主模式"分支 → 自己收完就返回
  ⇒ **返回 `0`**。

两个现象同时出现时，"通信失败"解释不了从机返回 `0`。

## 判定方法

1. **grep 配置宏名的引用点**：若只命中 `#define` 行 → 该宏是死代码，配置对象极可能漏初始化。
2. **从返回值语义反推**：
   - 从设备侧返回 **`0`**（而非 `-EINPROGRESS` / 有界超时如 `-115`）⇒ 它**根本没在等**，
     优先怀疑"它其实跑在主模式 / 配置对象是空的"，而不是"它等不到时钟"。
   - 返回**有界超时**才说明"真在等，只是没等到"。
3. 对照同类驱动（如另一个 STM32-like SPI 驱动）的同名路径，确认正常写法。

## 处理

把宏真正接到配置对象上（或删掉死宏、直接写显式字段）；用例侧保留"从设备必须报告
`-EINPROGRESS`/有界超时"这类**返回值语义断言**，让同类漏初始化下次自己暴露。
