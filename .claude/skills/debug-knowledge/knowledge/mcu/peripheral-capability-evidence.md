# 判定"外设有/没有某能力"的证据纪律

## 现象

为某外设写用例/驱动时，需要判断三件事：某实例**归哪个驱动**、某**复用/能力是否支持**、
某 DT 属性的**极性（enable 还是 disable）**。三件事都容易"看一眼/搜一下"就下结论，然后错。

## 根因

三个独立的认知陷阱叠加：

1. **按实例号推断归属**：同前缀的实例可能挂不同 `compatible`（同一 SoC 的 `spi1/2` 与
   `spi3/4` 常是两种 SPI IP）。实例号的连续性不保证驱动一致。
2. **按关键字名想当然搜**：片选在有的 SoC 命名是 `NSS`、有的是 `CSN`、`CS`、`FSS`；
   驱动里出现的 `*_mtu_get()` 也可能根本没挂进 `api`。**在同一个文件里"找过但没找到"**
   被当成了"不存在"。
3. **按属性名推断极性**：`*_caps_mask` / `*_disable_mask` 这类名字不说明极性；
   `caps_mask = 0x40000` 既可能是"打开第 18 位能力"也可能是"关掉第 18 位能力"。

## 判定方法

- **归属**：`grep -n "<实例 label>" <soc>.dtsi`，读该节点的 **`compatible`**，再按
  `DT_DRV_COMPAT` 反查驱动文件。SPI↔SPIF 类"配对控制器"用 `<配对者>.spi = <&spiN>` 反查。
- **能力**：关键字**全集**检索（如片选：`NSS|CSN|CS|SS|FSS|片选`），且确认检索词覆盖了
  该 IP 家族的全部命名变体；结论写进文档时**附检索表达式**，不写"我搜过了"。
  另：**驱动文件里存在某函数 ≠ 该函数被挂进 ops**——要顺 `api` 结构体确认可达性。
- **极性**：读到 caps/mask 类属性，**先看 binding 位表的措辞**（"bit N : enable …" vs
  "bit N : disable …"），再看驱动是 `&` 还是 `~(…) &`。位表 + 驱动表达式两处一致才算定论。
- **交叉印证**：编译产物（`build/zephyr/zephyr.dts`、`.config`、驱动结构体初值）比源码推理更硬。

## 处理

按上述三问逐项取证；结论按"**仓库可证**"与"**只有实测/接线能定**"分级标注，
后者不得写成硬编码断言。
