# 嵌入式调试方法论（通用，不依赖硬件环境）

跨芯片、跨工程、跨环境的调试方法学。**适用于任何嵌入式开发环境的"定位问题"**；
具体到 QSH/810 的连接层、烧录、串口细节，见 `qsh-debug`
（QSH 调试主入口；scons/HAL 低频验证见其附 `ref-scons-hal-verify.md`）——它们是本方法学在
某套硬件环境上的实例化。

## 0. 调试总流程（先走流程，再动手）

```text
1. 确认环境链路   连得上、烧得进、日志有输出？环境问题先于一切
2. 复现抓现象     稳定复现 + 记录原始输出（勿只看加工后的结论）
3. 分层定位 §1    自上而下：应用→驱动/中间层→硬件，每层排除后再下沉
4. 断点抓现场 §2  断在"状态被破坏之前"，一轮只抓一个时刻
5. 双通道验证 §3  内存事实 + 执行事实交叉，可信才动手修
6. 修复 → 验证 → 探针清理（§4）→ 沉淀（§6）
```

## 1. 分层根因定位方法学

**自上而下，每层确认排除后再下沉一层；驱动/固件行为先读源码确认机制，不要猜。**

### 1.1 应用层（业务/测试代码）
- 报错线索先查业务层是否给了归因（token/reason/错误码）——先信它指向的方向，但**警惕弱校验造成的假 PASS**（只校验部分字段/不看返回值/断言无期望值对比的，结果不可信）
- 用"谁先错"定位：对端 vs 本侧各自的计数/标志对比，区分是 A 侧没发还是 B 侧没收到，不是只看单侧

### 1.2 驱动/中间层
- 读 ISR 分发顺序：中断标志位的**判定顺序**决定事件优先级，先判定的分支吃掉后判定的事件是常见 bug
- 读数据路径与状态机：缓冲模型、FIFO 续写、状态迁移守卫
- 重点找"回调里无条件赋值/覆盖"类代码：常在 stop/end 类回调里把对侧设置的参数无条件重置——用断点对比"请求时刻 vs 结束时刻"的变量值即可证实（§2）

### 1.3 硬件层（寄存器 + 波形）
- 外设寄存器直接读内存（基址+偏移），偏移/位域含义查 reg 头文件
- **寄存器读"全对" ≠ 总线没问题**：总线时序问题（高电平起不来/上升沿慢/偶发 EIO）
  用示波器/逻辑分析仪，**示波器优先级高于寄存器断点**（§3.3）
- **软件复位救不活的状态，先查它落在哪个时钟/电源域、该复位是否覆盖**：模块级复位线常不
  覆盖 pad/IO 电气配置（开漏/推挽/上下拉多在独立常开/电源域），只有整板/全芯片复位才清——
  **别急着归因"硅级 erratum"**（判断：复位前后该寄存器值不变 ⇒ 未被该复位覆盖）
- **下"本层无关"结论前，确认扫描覆盖本层全部相关寄存器**：从本层代码路径（函数调用）穷举
  到底层寄存器地址，而非从手册挑"疑似相关"的子集（判断：扫描集 = 代码实际写到的寄存器全集；
  漏扫一个方向/电气寄存器就会得出错误的"本层无关"）

### 1.4 多来源二分隔离（变量隔离法）

现象可能来自多个来源（共享资源副作用 / 总线瞬态毛刺 / 自身状态残留）时，**不要一路深挖
单一假设**；用隔离实验逐个排除，**每个实验只动一个变量**：
- 换一个与故障"不相干"的同类模块（不同引脚/不同实例）→ 故障不变 ⇒ 排除系统性副作用
- 物理断开总线/对端 → 仍失败 ⇒ 排除总线瞬态毛刺
- 只扫自身寄存器 diff（切换前后对比）→ 锁定自身残留状态

判断标准：每个实验只允许一个变量变化，"复现/消失"的边界才可信；越过二分直接下"硅级
erratum"结论是典型误判。实例：引脚复用双状态切换后通信失效（`debug-knowledge` mcu 域实例 #1）。

## 2. 断点抓现场法（定位硬件/驱动状态的关键手段）

**核心原则：断在"状态被破坏之前"**。反例：断在结果记账函数——命中时 stop/end
回调早已把计数器清零、长度恢复默认，抓到的是结束后的状态不是现场。正例：断在
请求到达回调，命中时缓冲/长度变量还是请求时刻的真实值。

要点：
- **一轮断点只抓一个时刻**；命中后读现场、`detach` 让目标继续跑，避免影响时序
- 目标固件无调试信息时：`nm <elf> | grep <symbol>` 查链接地址（链接地址=加载地址），
  用裸地址断点 `break *0x<addr>`
- 需要验证"哪个分支被执行"时，直接断在该分支代码处而非回调入口
- 变量读有符号（`x/dw`/`x/dh`），寄存器读无符号（`x/wx`），数组 `x/Nbx`
- 临时调试脚本用完必须清理（§4）

## 3. 证据与波形：双通道验证

### 3.1 双通道交叉（结果可信的前提）
- **内存事实（dump/断点读） + 执行事实（串口/日志输出）** 独立取证，两边一致才算过；
  两边用同一判定变量/符号，避免各看各的
- 两边矛盾时**先怀疑工具瞬态**（内存读有"2 word 读错、重跑即消"类先例），重跑一次
  确认，不要立刻怀疑代码

### 3.2 日志采集纪律
- 采集窗口必须覆盖程序运行全程：**先启动采集，再启动程序**
- 输出含 shell/控制台重绘 ANSI 时，解析先剥离 `\x1b\[[0-9;?]*[A-Za-z]`，行匹配用
  `re.search()` 不用 `^` 锚点（行首可能被提示符污染）
- 判定关键字出现前可能有前缀，先验证真实格式再写解析

### 3.3 电路层排查（软件全对 + 波形异常时转入，方法学 M1）
- 触发：寄存器读全符合预期，但总线波形异常 → **软件侧推导电路变化**：对端切走模式
  （协议切走/掉电/GPIO 变更）→ 其内部上拉/端接消失 → 并联等效阻抗变（R/2 → 单侧 R）
  → RC 超位时间。实例：I3C 双路对接对端切走后回 I3C -EIO，根因是总线只剩单侧 ~1KΩ、
  40ns 高电平拉不上
- 规避方向：上拉降挡/加大 IO 驱动/外部电阻
- 新坑按"命中方法学挂实例 / 新开速查行"归档（§6）

## 4. 探针纪律（防污染其他工程）

- 调试插桩（调试日志/计数器/GPIO 标记/while(1) 陷阱/临时 probe 脚本）**调试完必须清理**：
  被插桩的共享文件用版本控制 `git checkout` 恢复；手工删的 `grep` 确认无残留
- **功能修复与调试残留要区分**：驱动/SoC 层的功能修复（workaround/写保护等）必须保留；
  调试残留一律删。用 `git diff` 逐文件甄别
- 通用调试脚本 vs 一次性调查产物要分家：别人/别的工程会直接调用的 → 留 scripts/ 永久
  提交；一次性调查产物 → 放 gitignore 的 tmp 目录，用完不必删但也不提交

## 5. 注释边界（★ 只写本层语义，不写外部历史）

给驱动/固件**新增/修改注释**时遵守职责边界：只描述**本层（驱动/固件）的行为语义与契约**，
不得把属于外部系统（OS 框架、历史 bug、调试过程、环境问题）的原因写进本层注释。

判断标准：**"如果这段代码换到别的工程/别的 OS 配置下，这条注释还成立吗？"** 不成立就
不该写在本层。

- **应该写**：协议语义、硬件行为约束、设计约束
- **不应该写**：OS 层问题（某框架 bug 已修）、调试历史（之前 LOG 阻塞 10ms…）、环境问题
  （Windows 管道缓冲…）
- **外部原因的归处**：反复会踩的通用坑 → §6 速查/顶层 CLAUDE.md；一次性定位闭环的 bug →
  问题总结 .md（§6）；调试临时注释 → 按 §4 探针纪律清理，不得随功能代码提交

## 6. 坑沉淀准则（分三类归档）

| 结果类型 | 归处 | 判断 |
|---|---|---|
| 一次性 bug（本次闭环后不会再遇到） | 问题总结 .md 存档 | 不会再踩 → 不进速查/知识库 |
| 通用环境/工具链坑（反复会踩） | 本 skill §7 + 顶层 CLAUDE.md §10 | 换机器/换环境还踩 → 沉淀 |
| **领域可复用调试法**（某域反复会用的招式） | **自调 `debug-knowledge` §写入 归入对应域** | 换板/换项目/换驱动还踩，且属 mcu/zephyr/linux/riscv/arm 某域 |

判断总标准：**换机器/换工程/换驱动会不会再踩？** 不会再踩就不沉淀；会再踩的，
再按上面"通用坑 vs 领域招式"决定放哪。
