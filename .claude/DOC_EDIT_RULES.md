# 文档编辑规范

> **目的**：确保文档结构清晰、内容不重复、易于维护
>
> **适用**：所有 CLAUDE.md、SKILL.md、SPEC_REFERENCE.md 等文档的编辑
>
> **SKILL.md 写作原则**（借鉴 Warp）：写原则，不写规则。把 skill 当成在指导一个聪明人，
> 而不是在给计算机编程。方向性指引比穷举规则管用。把"为什么"讲清楚，agent 就能推理，
> 而不是死板执行指令。

---

## 1. 文档层级与职责

| 文档 | 职责 | 内容类型 | 更新频率 |
|------|------|---------|---------|
| **CLAUDE.md** | 快速上手入口 | 概览、核心规范速查、文档索引 | 低（结构性变更） |
| **SPEC_REFERENCE.md** | 详细技术规范 | 完整的规范、原理、实现细节 | 中（规范变更） |
| **KNOWN_ISSUES.md** | 问题清单 | 已知坑、解决方案、调试技巧 | 高（持续积累） |
| **HARDWARE_SETUP.md** | 硬件环境 | 接线、COM映射、DebugServer配置 | 低（硬件变更） |
| **.claude/CLAUDE.md** | Skill 库便携说明 | skill 库结构、加载机制、迁移指南 | 极低（🔒保护） |
| **.claude/skills/*/SKILL.md** | 各 skill 使用说明 | skill 的功能、用法、示例 | 中（skill 更新） |

## 2. 内容归属规则

### 2.1 写入 CLAUDE.md 的内容

✅ **应该写入**：
- 项目概览（1-2句话）
- 核心规范速查（最常用、最易踩坑的 5-10 条）
- 测试工程列表（简洁列表，不含详细说明）
- 调用入口命令（最常用的 3-5 个）
- 文档索引（链接到其他文档）

❌ **不应该写入**：
- 详细的实现原理 → `SPEC_REFERENCE.md`
- 完整的问题清单 → `KNOWN_ISSUES.md`
- 详细的硬件配置步骤 → `HARDWARE_SETUP.md`
- 具体的 skill 使用方法 → `.claude/skills/*/SKILL.md`

### 2.2 写入 SPEC_REFERENCE.md 的内容

✅ **应该写入**：
- 完整的固件编写规范（所有细节）
- 结果判定标准的完整说明
- 覆盖矩阵与预期数据
- XIP 烧录详细步骤
- 命令协议完整定义

### 2.3 写入 KNOWN_ISSUES.md 的内容

✅ **应该写入**：
- 所有已知坑（完整清单）
- 每个坑的详细描述、原因、解决方案
- 调试技巧和排查方法
- 环境问题的完整记录

### 2.4 写入 SKILL.md 的内容

✅ **应该写入**：
- skill 的功能描述
- 使用方法和参数说明
- 完整的示例代码
- 常见问题（skill 特定）

## 3. 编辑原则

### 3.0 精简铁律（所有文档适用）

**禁止写入**（对 agent 无用，白占上下文）：
- 最后更新日期、维护者署名（git log 自带，无需文档记录）
- 纯装饰性分隔线（`---` 用于视觉隔开，无结构意义时删掉）
- "请务必遵守"、"请注意" 等礼貌性缓冲词（用"必须"/"禁止"直接表达）
- 重复的免责声明（同一警告只在源头写一次，其他地方链接）

**新增内容自检**：每条新内容是否回答了 agent 的具体问题？不回答任何问题的一律不加。

### 3.1 精简原则

**CLAUDE.md 行数预算**：按 keeper §2 加载层级，硬性上限 **≤200 行**（任何 CLAUDE.md）

- ✅ 使用表格、列表压缩信息
- ✅ 详细内容用链接引用
- ❌ 避免大段文字描述
- ❌ 避免重复其他文档的内容

**示例**：
```markdown
# ❌ 不好（详细描述）
I3C dualcore test 是一个双核测试工程，包含 8 个 case，
主要测试 I3C 跨核通信的 pure 和 mixed 模式，速率从 400k 到 12.5M...

# ✅ 好（简洁列表）
**双核**：i3c_dualcore_test(8), i2c_pure_test(1)
详细说明：见各工程的 README.md
```

### 3.2 单一信息源原则

**同一信息只在一个地方维护**：

| 信息类型 | 唯一来源 | 其他地方 |
|---------|---------|---------|
| 串口映射规则 | `HARDWARE_SETUP.md` | CLAUDE.md 只链接 |
| 固件编写规范 | `SPEC_REFERENCE.md` | CLAUDE.md 只列核心速查 |
| 已知坑清单 | `KNOWN_ISSUES.md` | CLAUDE.md 只列最常见的 5 条 |
| Skill 使用方法 | `SKILL.md` | 其他文档只链接 |

**违反示例**：
```markdown
# ❌ 不好（重复维护）
CLAUDE.md:          完整列出 36 条已知坑
KNOWN_ISSUES.md:    完整列出 36 条已知坑（重复）

# ✅ 好（单一来源）
CLAUDE.md:          列出最常见的 5 条 + 链接到完整版
KNOWN_ISSUES.md:    完整列出 36 条（唯一来源）
```

### 3.3 核心规范速查规则

**CLAUDE.md §4 核心规范速查**应该包含：
- 最常用（80% 场景需要）
- 最易踩坑（踩过多次）
- 最重要（不遵守会导致严重问题）

**不应该包含**：
- 只在特定场景使用的规范
- 详细的技术原理
- 可以通过推理得出的规范

### 3.4 一次性事故不入文档/注释（与 SPEC_REFERENCE §6.1.6 同原则）

文档与代码注释只记录两类长期价值内容：**a) 驱动/硬件层面需注意的问题；b) 应用层面易反复出现的问题**。
一次性操作事故（含日期的修复史、"一度/曾经/某次迁移"类叙述）不写入任何规范文档与代码注释；
保留"是什么/为什么必须这样"的结构约束，删除"曾经发生过什么事故"。
坑沉淀三分法（一次性/通用环境/可复用调试法）见 embedded-debug §6、debug-knowledge §写入——口径一致。

### 3.5 驱动代码注释内容规范（严格）

> 适用范围：zephyr/drivers/、modules/hal/、soc/ 等底层驱动代码。应用代码（测试固件、sample）不受此约束。

**驱动注释会被 GitLab review / 上游社区审查，必须经得起时间考验。**

**必须遵守：**
- 只写**本层**的语义和约束 —— 如果这段代码搬到别的 OS 还成立吗？不成立就不写
- 说明 **WHY**（设计约束/硬件行为），不写 HOW（实现步骤、调试过程）
- 一句话能说清的不写三句；引用硬件寄存器/标志名要直接

**禁止出现：**
- 临时调试标记（`★` / `HACK` / `TEMP` 等装饰符号）
- 带日期的修复叙事（"上次测试发现...所以改成..."）
- 引用外部系统行为作为理由（应描述本层约束，而非外部依赖的行为）
- 逐步操作描述（像 CHANGELOG 一样的实现步骤列举）

**格式**：C89 `/* */` 块注释，`/** */` Doxygen 用于公开函数，tabs 缩进。

**参照风格**（原厂代码 MATCHSS 注释模式）：
```c
/* IBI 完成等待超时：总线忙时请求要排队等仲裁（如主机正在 ENTDAA
 * 长帧链、或大读传输期间），仲裁等待可达数 ms~数十 ms；超时路径会
 * 撤销 SCTRL.EVENT 请求，过短会把仍在合法等仲裁的 IBI 误杀。
 * 100ms 覆盖 DAA 场景，也是主机不存在时 ibi_raise 不永久阻塞的兜底。 */
```
结构：一句话核心原因 → 关键硬件行为/约束 → 取值/结论。

## 4. 更新流程

### 4.1 新增规范/功能

```
1. 确定内容归属（见 §2）
2. 写入对应的详细文档（SPEC_REFERENCE.md / KNOWN_ISSUES.md / SKILL.md）
3. 如果是核心规范 → 在 CLAUDE.md §4 添加速查条目（1行）
4. 如果不是核心规范 → 只在详细文档中添加，CLAUDE.md 不动
```

### 4.2 修改现有内容

```
1. 确定内容的唯一来源（见 §3.2）
2. 只修改唯一来源
3. 检查其他文档是否需要更新链接或引用
```

### 4.3 删除内容

```
1. 确认内容已过时或不适用
2. 从唯一来源删除
3. 检查其他文档是否引用了该内容，一并删除
```

## 5. 检查清单

编辑前自检：

- [ ] 这个内容应该写在哪个文档？（见 §2）
- [ ] 是否已经在其他文档中存在？（避免重复）
- [ ] 如果是 CLAUDE.md，是否应该只添加速查条目？
- [ ] 是否违反了单一信息源原则？
- [ ] 是否会导致 CLAUDE.md 超过层级行数预算（keeper §2）？

编辑后自检：

- [ ] CLAUDE.md 是否仍然精简？
- [ ] 详细内容是否在正确的文档中？
- [ ] 链接是否正确？
- [ ] 是否有重复内容？
- [ ] 若新增了判据/校验规则，是否按 keeper §0 铁律 #10 做了双向自测？

## 6. 常见问题

### Q1: 这个规范应该写在哪里？

**决策树**：
```
是核心规范（最常用/易踩坑/重要）？
├─ 是 → CLAUDE.md §4 添加速查（1行） + SPEC_REFERENCE.md 详细说明
└─ 否 → 只写入 SPEC_REFERENCE.md
```

### Q2: CLAUDE.md 超过层级行数预算怎么办？

**优化策略**：
1. 检查是否有可以链接化的详细内容（降级到 L2）
2. 检查是否有重复其他文档的内容（单一信息源）
3. 检查表格/列表是否可以压缩
4. 参考 keeper §2.3 内容放置决策树

### Q3: 新增 skill 时应该更新哪些文档？

**更新清单**：
1. 创建 `.claude/skills/<name>/SKILL.md`
2. 更新 `.claude/TOOLS_AND_SKILLS.md`（添加 skill 列表项）
3. 更新 `.claude/CLAUDE.md`（仅当 skill 库结构变更时，🔒保护文档）
4. 如果是核心功能 → CLAUDE.md §2 添加一行说明

## 7. 违规示例

### ❌ 违规1：重复维护
```markdown
CLAUDE.md:          完整的 36 条已知坑
KNOWN_ISSUES.md:    完整的 36 条已知坑
```
**问题**：两处维护，容易不同步

### ❌ 违规2：CLAUDE.md 过于详细
```markdown
CLAUDE.md:          详细描述 I3C 协议原理（50行）
```
**问题**：应该放在 SPEC_REFERENCE.md

### ❌ 违规3：缺少速查
```markdown
CLAUDE.md:          只有链接，没有核心规范速查
```
**问题**：容易忽略关键规范

## 8. 保护文档特殊规则

**`.claude/CLAUDE.md`**（🔒 保护文档）：
- ✅ 仅在 skill 库结构变更时修改（新增/删除 skill、目录调整）
- ❌ 禁止添加业务规范、测试规则
- ❌ 禁止添加单个 skill 的使用说明
- 📝 修改前必须确认影响范围

**`common/common_sources.cmake`**（🔒 保护文档）：
- ✅ 仅在新增/删除公共模块时修改
- ❌ 禁止添加工程特定配置
- 📝 修改后需验证所有工程能正常构建
