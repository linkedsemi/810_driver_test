QUEUE SIZE UNIT / CAPACITY
  shell_backend.h:75-79:
    static uint32_t _name##_buf[_queue_size / sizeof(uint32_t)];
    .size = ARRAY_SIZE(_name##_buf);   // .size is WORDS
  => QUEUE_SIZE is BYTES. 512 B = 128 words; 64 B = 16 words.
     The customer's "512 words" would be 2048 B, 4x the actual byte size.
  Measured slots: L4e (TIMEOUT=0, full queue) keeps ~11-12 messages => 512 B / ~12
    ~= 43 B/msg ~= 10.7 words/msg. Consistent with 200 messages fitting in the 8 KB
    log ring (wlen <= 40.96 B). At ~40 B/msg: 512 B ~= 12 slots, 64 B ~= 1 slot.
    "512 words" would predict ~50 slots at 40 B/msg, ~4x too many.
  Note: the first-slowdown method does not work here: with TIMEOUT>0 the producer
    waits on the sem and the queue never overflows; the pace is uniform from msg 0.
    L4e (TIMEOUT=0) exposes the capacity by overwrite (11-12 survivors).

L1 vs L5 (length control)
  Both show the same pattern: uniform arrival, no fast->slow transition, no TIMEOUT
  scaling. Only the absolute pitch scales with the line: 7.5 ms (65 chars / ~92 B)
  vs 14.6 ms (146 chars / ~168 B), i.e. UART-limited. So length is NOT the necessary
  condition for the customer's pattern; the short-message L1 already lacks it.
