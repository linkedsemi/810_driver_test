# O-35 离线定性：i2c filter「就地改写已在用通道的授权地址疑似不生效」

- **日期**：2026-09-23
- **类型**：**纯离线源码定性**（未上板、未构建、未改任何代码；全部 git 子命令只读）
- **被定性假设**：`linkedsemi_i2c_filter_fill_bitmap()` 对**已启用通道**做"改地址"时不生效
- **结论（一句话）**：**③ 代码上排除了该假设的"软件层"版本** —— 驱动侧无任何"已启用则拒绝/跳过"的守卫，
  就地改址与新通道走**逐字节同一条**路径且返回 `0`；**且实测对照本身被"热身"污染**，现象另有解释。
  **HW 层**（"地址寄存器在使能中被硬件忽略"）源码无法判定，属**残余未定项**，附寄存器清单（见 §6）。

## 1. Q1：`fill_bitmap` 写地址时有没有"该通道已启用则拒绝/跳过"的守卫？

### 结论：**没有。**（可定论，源码级）

`i2c_filter.c:134-188` 的 `fill_bitmap()` 全部守卫只有两处：

| 行 | 守卫 | 返回 |
|---|---|---|
| `:142-144` | `idx > (LINKEDSEMI_I2C_F_ADDR_NUM - 1)`（即 >15） | `-EINVAL` |
| `:145-148` | `bitmap == NULL` | `-EINVAL` |

**唯一的拒绝路径**是重址扫描 `:152-166`，而它**明确豁免通道自身**：

```c
:157   if ((wht_addr.field[addr_idx].WHITELIST_ADDRESS == addr) && (it_idx != idx)) {
:159       if (smbf_address_enable & BIT(it_idx)) {
:160-162       DEV_ERR(...); return -EINVAL;    /* "addr is duplicated with channel N" */
```

⇒ 判据是**"别人（`it_idx != idx`）处于使能态且占了同址"**，**不是"自己已使能"**。
**改写一个已在用的通道在驱动里是被显式允许的**（同址填回自己也放行 —— 这一点在
`duplicate_addr_rejected` 用例 `i2cf_test.c:329` 已被实测覆盖）。

此外 `:181-183` 在填表末尾**无条件**把本通道 enable 置位（读-改-写 `|= BIT(idx)`），
也不存在"已使能则跳过"。

### ①级交叉印证（关键）

`i2c_failure_triage.md:370`（§9.2 第 ⑤ 行）记录：就地改址变体 FAIL 的断言行是
**`ret_authorized` 那一条**（`zassert_ok(ret_authorized, …)`），**而不是它前面的
`zassert_ok(linkedsemi_i2c_filter_fill_bitmap(dev, 0, slave, bm), …)`**。

> ⇒ **实测反证了"驱动拒绝了这次就地改址"**：若守卫拦下，`fill_bitmap` 会返回 `-EINVAL`、
> 失败点会落在 fill 那一行。失败点落在**后一笔读**上 ⇒ `fill_bitmap` 返回了 `0`，
> **驱动确实发出了就地改址的寄存器写入序列**。

## 2. Q2：写入路径是否依赖"只在通道未启用时才成立"的状态？

### 软件层：**看不出任何此类依赖**（可定论）
### 硬件层：**看不出，需上板**（不可定论）

`fill_bitmap` 在拿到 mutex 后是一段**平铺的 MMIO 写序列，无任何按使能位的分支、无轮询、无延迟、无回读校验**：

| 行 | 动作 |
|---|---|
| `:168-172` | 对 `WHITELIST_ADDRESS_3_0 + ((idx>>2)<<2)` 做**读-改-写**，只改 `field[idx % 4]` |
| `:174` | 写 `SMBF_ADDRESS_INDEX = idx`（命令表**窗口选择**） |
| `:175-179` | 向 `WHITELIST_COMMAND_0..7`（窗口寄存器 `0x00..0x1c`）连写 8 个字 |
| `:181-183` | 读-改-写 `SMBF_ADDRESS_ENABLE \|= BIT(idx)` |

全函数**不读 `SMBUS_FILTER_SET`、不读 `SMBF_REG_ENABLE`、不读使能位、无 `if (enabled)` 分支**。

**因此，软件侧不存在"必须先 disable 才能写地址"的顺序要求** —— 这一段是**可定论的**。

**但"硬件是否要求先 disable"无法从源码判定**：`reg_i2c_filter.h` 对
`WHITELIST_ADDRESS_3_0`（`:18`）、`SMBF_ADDRESS_ENABLE`（`:26`）、`SMBF_ADDRESS_INDEX`（`:23`）
**只给出字段名与位宽，没有任何行为语义**（此限制在 `KNOWN_ISSUES.md:1413-1419` 已被登记，
适用面完全相同：**③级推断，不得作结论**）。

**旁证（②级，仅提示不做判据）**：两个厂商样例在 fill 之前都把器件置于"未使能"侧 ——
`i2c_filter_loopback/src/main.c:163` 先 `_en(i2cfilter, false, …)` 再 `:164` fill；
`samples/i2c_filter/src/main.c:41` 先 `enable_channel(index, false)` 再 `:57` fill。
**但两个样例都从不改已使能通道的地址**（loopback 每轮都写同一个 `i2ctargeteeprom2_addr`；
`i2c_filter` 写死常量 `addr = 0x50`）⇒ ②级证据对"是否必须 disable 后写"**既不证实也不否定**。

**附带可定论的一点**：`fill_bitmap` **对自己写下去的内容不做任何回读校验**（对比 `dump_bitmap`
`:190-222` 是有回读的）。⇒ **"驱动返回 0" ≠ "寄存器已生效"**。这不是缺陷，但它正是本假设
难以在软件层自证/自否的原因 —— 任何被静默丢弃的写,驱动侧**看不见**。

## 3. Q3：调用方用法顺序（fill 时滤波器 on/off）与驱动的要求

| 调用方 | fill 时的滤波器状态 | 依据 |
|---|---|---|
| `i2cf_test.c` 最终版 `filter_blocks_nonwhitelist` | **off**（``:962` `i2cf_filter_off()` → `:963` fill） | BLOCK_DISABLE=1, FILTER_DISABLE=1 |
| 变体 ⑤（就地改址） | **off**（同上序列，据 §9.1 改动记录推断） | ⚠ 该变体源码**未提交、已不可考**；此格为**推断**，非观测 |
| `filter_passthrough_whitelist` | **off**（`i2cf_reset_all` 后 `cold_reset` 收尾即 `_en(false,false,true)`，`:345`） | `i2c_filter.c:292-349` |
| 厂商 loopback 样例 | **off**（`main.c:163` 显式关，`:169` 开） | ②级 |

**驱动对滤波器 on/off 状态无任何要求**：`fill_bitmap` 既不读也不写 `SMBUS_FILTER_SET` /
`SMBF_REG_ENABLE`，只取 `dev_data->lock`（`:150`）。⇒ 任何状态都被接受。

> **这是本项最关键的一处排除**：变体 ⑤（就地改址）与变体 ⑦（新增通道）**处于完全相同的滤波器状态
> （off）**、相同通路、相同发起方、相同目标地址。⇒ **"滤波器开关状态"不是两者结果差异的解释变量。**

## 4. Q4：能否从代码上解释"改址不生效、但新增通道生效"？

### 结论：**不能。两条独立理由。**

### 4.1 代码路径逐字节相同（源码级，可定论）

`fill_bitmap` **没有任何分支的走向取决于 `idx` 此前是否已使能**。
更进一步：`idx=0` 与 `idx=1` 连**寄存器落点都相同** —— `offset = (idx>>2)<<2` 对两者都是 `0`
（`:168`），两次写的是**同一个** `WHITELIST_ADDRESS_3_0`（一个改 byte0、一个改 byte1）；
命令表窗口选择、8 字写、使能置位的代码完全相同。
唯一有条件的重址扫描在两种情形下**都放行**（就地改址时自己的槽位被 `:157` 的 `it_idx != idx` 豁免；
且 `i2cf_reset_all` 已把 16 个通道全关，不存在**其它**占着 `0x33` 的已使能通道）。

> ⇒ **源码里不存在能产生该差异的机构。** 若差异真实存在，它只可能在**寄存器写入之下**（硬件比较器/
> 查表刷新时机），而不在代码里。

### 4.2 更重要的：**实测对照本身被"热身"污染**（①级）

`i2c_failure_triage.md:361-374`（§9.2 表）逐次结果：

| # | 实现 | 结果 |
|---|---|---|
| ⑤ | **就地改 ch0**（0x2A→0x33）+ burst（**无热身**） | **FAIL** |
| ⑥ | **新增 ch1** + burst（**无热身**） | **FAIL** ← ★ |
| ⑦ | 新增 ch1 + **热身一笔** + burst | **PASS 18/18** |
| ⑧⑨ | 最终版复跑 ×2 | **PASS 18/18** |

> ★ **⑥ 是决定性的**：它与"正常的"®同为一个处理（**新增通道**），**且同样 FAIL**。
> ⇒ **唯一 PASS 的三个样本全都带"热身"，而"新增通道"在无热身时与"就地改址"一样失败。**
> ⇒ **"就地改址 vs 新增通道"这一对照，被"判读笔之前是否有热身"污染**，
> **不能作为判据**。

而 §9.3 规律 1（`i2c_failure_triage.md:388-393`）已独立给出了充分解释：
**紧接一次被拦（NACK）事务之后的下一笔，本通路上 10 次里 9 次 `-EIO`**（含中间隔冷复位的情形），
**再下一笔 5/5 正常**。变体 ⑤ 的判读笔**正落在该位置**（主判据 `ret_blocked < 0` 的拦截笔之后）
⇒ ⑤ 的 `-EIO` **无需引入任何"改址未生效"假设即可解释**。
当前源码 `:947-951` / `:968-970` 正是为此加入热身并注明"热身结果丢弃、不进判据"。

### 4.3 小结

- **软件层的假设**（"驱动因通道已使能而没写/被拒"）—— **代码上排除**（§1、§4.1），且有 ①级印证（§1）。
- **现象层的假设**（"改址不生效"）—— **实测证据不支持**：其对照被污染（§4.2）。
- **HW 层的假设**（"使能中写地址寄存器被硬件忽略"）—— **源码无法判定**，属残余未定项（§6）。

⇒ 该假设**当前处于"无证据支持"状态**（既非"疑似成立"，也非"已证伪"）。**不得作为结论引用。**

## 5. 建议的最小判别实验（**若要把 HW 层残余项也关掉**）

**成本极低**：现行 `i2cf_test.c` **已经**含热身（`:969-970`）。
把 `:963` 的 idx 由 `1` 改回 `0`（即回到变体 ⑤ 的语义），**其余一字不改**，重跑：

| 结果 | 含义 |
|---|---|
| **PASS**（`authorized_ret=0`） | 就地改址**在 HW 上生效** ⇒ 原假设**整体否定**（③） |
| **FAIL**（`-EIO`，且热身笔也是 `-EIO`） | 差异真有 HW 成分 ⇒ 转 §6 寄存器取证（②） |

## 6. 残余未定项：寄存器清单与期望值（仅当 §5 仍 FAIL，或需要直接定量时）

**基址**：`i2cf_reg_base(3)` = `DT_REG_ADDR(DT_NODELABEL(i2cf4))`；偏移取自 `reg_i2c_filter.h`。
**场景**：`i2cf_reset_all` → `i2cf_filter_off` → `fill_bitmap(dev, 0, 0x33, bm)`（**就地**，原 `0x2A`）。

| 寄存器 | 偏移 | 期望值 | 判读 | 判别力 |
|---|---|---|---|---|
| `WHITELIST_ADDRESS_3_0` | `0x34` | **`byte0[6:0] == 0x33`**（`field[0]`，idx=0） | 读回 `0x2A` ⇒ 地址写**未落**（HW 层假设成立）；读回 `0x33` ⇒ 写已落 | ★★★ **决定性** |
| `SMBF_ADDRESS_ENABLE` | `0x58` | **`0x1`**（fill 在 `:181-183` 无条件置位） | bit0 为 0 ⇒ 连使能写也丢了（更严重的写通路问题） | ★★ |
| `WHITELIST_COMMAND_0` | `0x00` | **`0xFFFFFFFF`**（`bitmap_all_on`；读之前先写 `SMBF_ADDRESS_INDEX=0`） | 读回 0 ⇒ 命令表窗口写未落 | ★★ |
| `SMBF_ADDRESS_INDEX` | `0x4c` | **`0`**（idx=0） | 窗口选择是否落 | ★ |
| `SMBUS_FILTER_SET` | `0x30` | **`0x3`**（fill 时 filter off：BLOCK_DISABLE=1, FILTER_DISABLE=1） | 确认 fill 时确处"关断"态（§3 的前提） | ★ |
| `INTR_STT` | `0x28` | 失败笔之后 `ADDRESS_BEYOND_WHITELIST == 1` | 为 0 ⇒ 该笔**根本不是白名单违规** ⇒ 支持"丢事务/位置效应"而非"表未更新" | ★★ |
| `SMBF_NONWHITELIST` | `0x50` | 非零，且 `ERROR_ADDRESS[15:8] == 0x33` | 全 0 ⇒ 未锁存违规 ⇒ 同上，支持位置效应 | ★★ |

⚠️ **注意判读力边界**：`SMBF_NONWHITELIST` 锁存的是**总线上出现的地址**，两种解释下都应为 `0x33`
⇒ 它**不能**区分"表里还是 0x2A"与"表里已是 0x33 但没刷新"，只能区分"是否发生过白名单违规"。

**零成本前置**：就地 fill 之后直接调 `linkedsemi_i2c_filter_dump_bitmap(dev, 0, &addr, dump)`
（`:190-222` 读的正是同一个 `WHITELIST_ADDRESS_3_0`）→ `addr` 期望 `0x33`。
⚠️ 但它只证明**地址寄存器已锁存**，**不证明比较器被刷新** ⇒ 仍以 §5 的总线级实验为准。

## 7. 旁证 / 未定（**不得当结论引用**）

1. **【旁证·未定】厂商样例的 fill 前置态**：两个样例 fill 前都处于"未使能"侧（§2）。
   但两者都不改已使能通道的地址 ⇒ 对"是否必须 disable 后写"**无判别力**。②级。
2. **【旁证·未定】驱动无回读校验**：`fill_bitmap` 不校验自己写的地址/位图（§2）。
   它不构成缺陷，但意味着"返回 0"不能当"已生效"用 —— 本假设正是卡在这条缝里。
3. **【旁证·已定论，但与本案无因果】`cold_reset` 表残留**：`cold_reset`（`:342-345`）只清
   **命令表**（`_en(…, clr_tbl=true)` 走 `:242-248`），**不清** `WHITELIST_ADDRESS_*` 与
   `SMBF_ADDRESS_ENABLE`；`fill_bitmap` 又**无条件**置使能位。⇒ 单独 `cold_reset` 后**旧地址仍在表里**。
   本测试的 `i2cf_reset_all`（`i2cf_test.c:128-136`）已用"显式关掉 16 个通道"规避。
   ⚠️ 由于重址守卫的判据是**使能位**（`:159`），**残留地址不会**误触发 `-EINVAL`
   ⇒ **与本案症状无因果关系**，仅登记。
4. **【覆盖缺口·旁证】现存全绿用例**（`fill_dump_roundtrip` / `duplicate_addr_rejected:329` /
   `concurrent_fill` 的 `conc_worker:566-583`）**都只重复写同一个地址**，
   **不覆盖"使能中改写为另一个地址"** ⇒ 本路径**当前无任何用例覆盖**，无论正反。
5. **【已定论·与本案无关】** 驱动历史提交 `761210e` "fix bug" 改的是
   `_en()` 里的 `MASTER_WRITE_MODE`（1→0，`:234`），与地址写通路无关。
