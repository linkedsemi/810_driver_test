## 1. DMA —— 通道配置被永久拒绝

### 1.1 失败的 case 在测什么

| case | 测什么 | 修复前 |
|---|---|---|
| `case_default` | DMA 通道配置、单次/循环传输、描述符链、多通道并发、非法通道号拒绝、配置后停止 | 1/7 |
| `case_destructive` | 大块传输、单字节传输、LLI 池耗尽、自拷贝拒绝、挂起/恢复守卫 | 4/9 |

### 1.2 测试场景

单核（cpu1）。测试依次对 DMA 控制器做**多轮配置→传输→停止**，每一轮复用同一批通道。
关键点：**通道是复用的**——上一个用例用完，下一个用例接着配。

### 1.3 本次现象

`case_default` 里 7 项只有 1 项通过，**11 个失败项中有 10 个是同一个原因**。

每次失败前，串口都先打出这一行：

```
<err> dma_dw_common: dmac@40041000: channel 0 must be inactive to reconfigure, currently 3
```

配置调用返回 `-EBUSY`。注意 `currently 3` —— 这是「通道处于 ACTIVE 状态」的编码。

**这 11 项不是 11 个 bug，是 1 个 bug 的 11 个表现。**

### 1.4 根因

DMA 通道的**软件状态机**永远回不到空闲态。

具体地：当传输配置启用了「完成回调」时，**传输完成中断从未被解除屏蔽**（解除屏蔽的代码被写在了一个分支里，只有不启用回调的模式才会执行到）。而该状态机的**唯一复位点，就在这个完成中断的处理函数里**。

于是链条是：

```
传输完成 → 硬件置位，但中断是屏蔽的 → 处理函数不执行 → 状态机不复位
        → 状态永久停在 ACTIVE → 下一次「配置」撞上 -EBUSY 守卫 → 拒绝
```

还有一条兜底也失效了：「停止通道」的早退分支在硬件已经完成时直接返回，**不复位状态机**。所以连"先 stop 再重配"这条退路也走不通。

**引入点**（`git log -S` 定死，**非本次新引入**）：

| 部件 | 提交 | 时间 |
|---|---|---|
| 完成中断分支 | `f9acacfd118`（Intel 原始实现） | — |
| `-EBUSY` 守卫 | `2f792c2de59`（上游 SOF 同步） | 2022-03 |
| 「停止」早退分支 | `58312e61043` | 2023-01 |

**为什么现在才暴露**：`dma_test.c` 在 **09-18** 把 `complete_callback_en` 从 0 改成 1，加严后潜伏缺陷**首次全面暴露**。
（09-17 之所以是绿的，是因为首个用例用「无回调」模式**永久解除**了中断屏蔽，后面的用例都在"搭便车"。）

### 1.5 修复

`zephyr/drivers/dma/dma_dw_common.c` / `.h`：

| # | 改动 |
|---|---|
| a | 完成中断的**解除屏蔽移出**分支，两种回调模式都解除屏蔽 |
| b | 配套：按模式**置空陈旧的回调指针**（成对做——否则中断会回调上一次配置留下的函数指针） |
| c | 「停止」早退分支：状态为 ACTIVE 时复位为空闲（**不动 PREPARED**，保住"配置→停止→启动"序列） |
| d | 恢复 `src == dst` 的显式拒绝（返回 `-EINVAL`），在主循环**之前**做前置遍历、比较**原始地址**、不产生副作用 |
| e | 块长掩码按变体正确划分（2.20a 用 10 位，其余保持 16 位、**零行为变化**） |

> 注 (e)：`modules/hal/linkedsemi/.../reg_dmacv3_type.h` 里的掩码常量（12 位）与实测冲突，按既有 `O-1` 裁定「只备注不修」，本次未动。

## 2. eMMC —— 非法请求泄漏互斥锁（P0）

### 2.1 失败的 case 在测什么

| case | 测什么 |
|---|---|
| `case_block_driver` | eMMC 块设备读写，DMA 传输模式 |
| `case_block_pio` | 同上，PIO 传输模式 |

两个 case 各 8/10，**失败项完全相同**。

### 2.2 测试场景

单核（cpu1）。用例集包含一组**边界/异常入参**检查，其中一项特意发一个**非法的数据操作码**，期望被拒绝（返回「不支持」）。

### 2.3 本次现象

```
INFO request_mutex_not_leaked: join=-11, probe_ret=2147483647, probe_ret2=2147483647, done=0
INFO set_io_clock_out_of_range_not_silent: f_min=50000, clock=1000, ret=0
```

两条线索：

1. **`join=-11`** —— 线程等待超时了。
2. **`probe_ret` 还是 `2147483647`** —— 这是初始哨兵值，**说明它从未被赋过值**：探针线程**第一次**发请求就没返回。

这是定位的关键：**锁在探针启动之前就已经被持有**。而紧邻它前面的那个用例（就是发非法操作码的那个）**自己是通过的**。

### 2.4 根因

**两个独立缺陷**（不在同一代码路径上）：

#### A. 非法操作码在持锁状态下提前返回（P0）

请求处理函数的加锁与解锁之间，包含一个 `default` 分支：遇到非法操作码直接返回「不支持」——**但跳过了解锁**。

因为用的是无限等待的加锁，**这个锁一旦泄漏就是永久阻塞**。

次生效应：一个「总线忙」标志再也不会被清零，导致 eMMC 的崩溃转储被**静默丢弃**。

**穷举结果**：全函数**有且仅有这 1 个泄漏点**。另两处提前返回（前置守卫、加锁失败）都在锁**外**，**不能**加解锁（会二次解锁导致崩溃）。

#### B. 越界时钟被静默忽略

设置 I/O 时钟时，若请求的频率超出合法范围，驱动**不改频、不报错、返回成功**。

这违反上游契约：Zephyr 自带的 SDHC 测试（`zephyr/tests/drivers/sdhc/src/main.c`）对同一行为有同样的断言，而 **linkedsemi 是全仓唯一违约的实现**。

### 2.5 修复

`zephyr/drivers/sdhc/sdhci-of-linkedsemi.c`：

| # | 改动 |
|---|---|
| ① | 新增数据操作码合法性检查函数 |
| ② | 在**加锁之前**拒绝非法操作码（消除 A 的成因，而不只是在出口补解锁） |
| ③ | `default` 分支改为跳转到统一解锁出口（防御性兜底） |
| ④ | 新增解锁标签，并把「清忙标志」移到标签**之后** |
| ⑤ | 越界时钟返回 `-EINVAL` 并打错误日志 |

> ⚠️ ④ 的方向容易搞反。`DEFECT_ANALYSIS_2026-09-17.md §4.6` 写的是「标签必须置于清忙标志**之后**」——按 C 语义这会让 `goto` **跳过**清除，反而制造次生缺陷。**建议更正该文档。**

### 2.6 验证

```bash
python run_test.py --case case_block_driver   # 8/10 → 10/10
python run_test.py --case case_block_pio      # 8/10 → 10/10
```

**三个「锁外拒绝」指纹全中**：

| 观察点 | 修复前 | 修复后 |
|---|---|---|
| `probe_ret` | `2147483647`（哨兵，从未赋值） | **`-134`** |
| `join` | `-11`（超时） | **`0`** |
| `done` | `0` | **`1`** |
| 越界时钟 `ret` | `0`（静默通过） | **`-22`** |

### 2.7 副作用评估

- 修复 A **不改变返回码**，只把拒绝时机从锁内提前到锁外；合法路径零改动。
- 修复 B 已穷举树内全部「设置 I/O 时钟」调用方（`sd.c` / `sd_ops.c` / `mmc.c` / `sdmmc.c` 共 13 处）——**无任何可达调用会传越界非零值**。（频率为 0 表示「保持当前」，始终放行；唯一会越界的高速模式被能力标志挡死。）

## 3. QSPI Flash —— 校准哨兵语义漂移（**新回归**）

### 3.1 失败的 case 在测什么

| case | 测什么 | 修复前 |
|---|---|---|
| `case_default` | 校准使能下的频率设置、读写往返（1B~8192B）、擦除、越界拒绝、原始读、分块读 | 14/26 |
| `case_no_calib` | **同上但关闭校准**，频率 25 MHz | 24/26 |

**这两个 case 唯一的差别就是校准开关** —— 这个对照本身是定位的关键。

### 3.2 本次现象

`case_default` 里从「设置频率」开始，探测 Flash 的 JEDEC ID 读回全零：

```
invalid jedec id 00 00 00    (×19)
re_init = -19
```

之后所有读写项（`rbuf != wbuf`）、擦除项、原始读、分块读**全线失败**。
而 `case_no_calib` 同频率、几乎同样的代码，**只有越界拒绝 2 项失败**。

### 3.3 根因

**两个独立根因。**

#### A. 校准哨兵的位置耦合被一次重排打破（10 项失败，**新回归**）

驱动里有个约定：当请求频率**低于**校准时钟时，走一个分支，把一个**哨兵值**写进"用哪组校准参数"的字段里。这个哨兵值的含义是「用参数表里的**第 0 项**」——也就是**参考捕获值**。

问题在于：**这个"第 0 项"是参考值，纯属当时表里的位置巧合。**

commit `75ff6a2a531`（**2026-09-08**）重排了这张表，把索引 0 从一个「参考捕获」换成了一个**校准自己判定为无效**的捕获组合。于是：

```
请求低频 → 写入哨兵 → 哨兵指向新表的第 0 项 = 坏捕获
        → 坏捕获被装进硬件 → JEDEC 探测失败 → 初始化返回 -19
        → 在探测处提前返回，走不到重新配置 → 坏捕获永久驻留，直到复位
```

**此后再也回不去**，后面 10 个用例全在坏捕获上跑。

**这条缺陷已经实际发作过一次**：同一个重排 commit **删掉了这个坑位的孪生兄弟**（另一处同样写哨兵值表示"用第 0 项"的代码）。**它移除了两处位置耦合中的一处，留下另一处对着新表继续跑。**

**`case_no_calib` 为什么幸免**：它校准关闭，那个字段恒为初值 0，捕获保持参考值。这**正面证明了参考捕获在本频率可用、坏的是新表第 0 项**。

#### B. 器件实际容量与用例常量不符（4 项失败）

越界拒绝那两项失败，**不是驱动缺校验**——校验是好的，而且编译进了固件（反汇编确认）。

真因：**用例按 32 MiB 构造越界地址，而器件实际是 64 MiB**。地址根本没越界，驱动自然不拒绝。

两路独立来源一致：串口直读 `64 MiBy flash` + JEDEC ID `20 40 20`。

### 3.4 修复

| 根因 | 改动 |
|---|---|
| A | `zephyr/drivers/spi/qspi_ls.c`：新增**具名参考哨兵**（值 `0xFE`）替代"表索引 0"的位置耦合；装载捕获时对该哨兵**直接写参考捕获值**，不再经过表。另加 3 行编译期断言锁死「哨兵不得与表项/无效值撞值」 |
| B | 用例侧：新增运行期容量推导（由 Flash 层布局推出），越界地址改用真实容量；并上报 `flash_size` 供核对 |

> **关于写法选择**：另有一种改法是"把哨兵改成表索引 1"（索引 1 恰好是参考值）。**明确不采用**——它仍把"参考捕获"编码为"表里的某个位置"，下次重排会以**完全相同的方式**静默复发。这正是本 bug 的成因。
> 正例对照：同族的 `spi_dw.c:139` 写的就是**参考值本身**，不经过任何表。

```

|---|---|---|
| 装载的捕获 | `cap_neg=1 cap_dly=0 (calib_combo=0x01)` | **`cap_neg=0 cap_dly=0 (calib_combo=0xfe)`** |

**新增的编译期断言已通过编译**（两 case 各自干净构建目录下均成功编译）。

### 3.6 附录

- 根因报告：`reports/2026-09-23-1/qspi_flash_test_case_default/qspi_flash_rootcause.md`（含 §8 复核）

## 4. WDT —— 「已配置」守卫被脉冲位残留污染

wdt_ls_setup: interrupt already configured
```

这说明两项都走了「已配置」守卫分支、返回「忙」。

### 4.3 根因

守卫判断「是否已配置」时，用的是**整个控制寄存器非零**。

而这个寄存器里除了使能位，还有**两个脉冲位**（"清中断"和"清计数"）。喂狗操作会写「清计数」位，**而硬件把这一位留 1、写 0 清不掉**（实测：进 disable 时 `0x0b`，写 0 后仍是 `0x08`——只清掉了使能位）。

于是残留的这一位让守卫**长期误判「已配置」**，恒返回「忙」。

**污染链**：唯一做「喂狗→关闭」的那个用例是污染源（它自己通过），**其后紧邻的两项成为受害者**。

另有一个用例因为「无超时应当被判不支持」的检查排在守卫**前面**，永远通过——**恰好把这个缺陷掩盖了**。

**非新回归**：该守卫自驱动诞生（2025-07-23）起就是这样，文件最近 6 次提交均未触碰，历史多轮报告失败项一致。

### 4.4 修复

`zephyr/drivers/watchdog/wdt_iwdg_ls.c`：守卫改为**只比较使能位**（`EN` 和 `RST_EN`），忽略脉冲位。

> **这不是放宽校验**：真正已配置（任一使能位为 1）仍返回「忙」。已逐条核对全仓期望「忙」的用例，**无 PASS→FAIL 翻转**。

### 4.5 验证

```bash
python run_test.py --case case_boundary          # 17/19 → 19/19
python run_test.py --case case_non_destructive   # 5/5（回归对照）
```

**一处需要修正的表述**：修复前的预期里写的是「日志不再出现 `interrupt already configured`」——**实测仍出现 1 次**，但那一次落在**合法的「忙」路径**上（第二次 setup 确实该被拒）。基线是 2 次，其中 1 次是误触发。
⇒ **准确表述应为「不再出现误触发」**。

## 5. SPIF —— 两态判据无法区分

### 5.1 直通模式切换（驱动缺陷，已修）

**测什么**：冷复位后，滤波器应处于「默认态」而非「直通态」——两态是互斥的。

**本次现象**：冷复位后，检查函数报告它**同时**处于两个状态。

**根因**：默认态与直通态在设备树里用的是**同一批引脚复用单元、同一个复用值**，10 个引脚**只差一个 `analog;` 属性**。而驱动的模式检查函数**只比较复用值，从不读引脚属性**——于是两个检查**恒等**，「互斥」的断言在构造上就不可能成立。

**这确实是驱动缺陷而非用例写错**：

- `analog` 属性会被引脚控制器落到**焊盘的模拟使能位**上；
- HAL **本来就提供**该位的回读接口（且实测符号已链进本工程）；
- **驱动自己在别处就把这个判据当「主机模式切换冲突」的守卫用**——它本该读。

**修复**：`modules/lib/pfr_tpm/drivers/pfr/spi/spi_filter.c` 的模式检查增加模拟使能位比对。
**该判据比原来更严**（只可能把「通过」翻成「不通过」），故对现有通过项是单调安全的。

**验证**：`passthrough_mode_switch` FAIL → **PASS**，串口 `passthrough` 由 `1` 变 **`0`**；`pinctrl_state_switch` 仍 PASS 作回归对照。

> 对应 `OPEN_ITEMS O-31`。**回退只需删掉那一个比对条件。**

### 5.2 命令槽位 DUMMY 字段（**已上板定性，待裁定**）

**测什么**：命令表的按索引访问——命令行、使能位、**DUMMY 周期数**都应按索引正确往返。

**本次现象**：索引 5 的槽位上，命令行 ✓、使能位 ✓、**DUMMY 周期数 ✗**。

**已排除**：驱动是标准读-改-写、无掩码缺陷；位域布局正确；索引与出参都合法。

**上板定性结果**：回读原始寄存器与取值**都是 `0`** ⇒ **该槽位的 DUMMY 字段不可写**。

**处置**：判据**未改动**。若确认迁到确有 DUMMY 相位的槽位（如索引 6/7），需裁定。
**此项基线就失败，非本次改动引入。**

## 7. 判定为「非驱动缺陷」的失败项

> 这一节的三项**不需要驱动侧改动**，列出来是为了避免下游把它们的现象误当驱动问题重复排查。

### 7.1 `i2cf_test / filter_blocks_nonwhitelist` —— **非驱动缺陷；已改用例**

**测什么**：滤波器开启时，上游访问白名单外的地址应被拦截。用例末尾还有一段"自证"，本意是证明**这次拦截确实来自白名单**，而不是"该地址本来就没有器件"。

**失败的是自证那一步**：它原本用「关掉滤波器后同一地址应能访问」来证明，而这个动作**在本通路上不成立**。

**为什么原自证步永远过不了**（**实测，非推断**）：

> **一笔被滤波器拦下（NACK）的事务之后，紧接的下一笔事务在本通路上多半会丢。**
> 该位置 **10 次里 9 次失败**（1 次成功）；**中间隔一次冷复位也一样**；而**再下一笔** 5/5 正常。

原自证步恰好就坐在"被拦之后紧接一笔"的位置上 —— **所以它怎么写都过不了**，与"关滤波器是否直通"无关。

**处置（已实施并上板验证）**：自证步改为**单变量对照** —— 保持"上游主机 / 经滤波器 / 同一地址 / 同一通路"**全部不变**，只把该地址**授权进白名单**，再读一次；并在正式对照读前加一笔**热身读**（结果丢弃、不进判据）。主判据（未授权地址必须被拒）**原样未动**，新断言**仍可失败**。

**验证**：上板 **`PASS 18/18`**（连跑 3 次）。

> ⚠️ **结论更正留痕**：本节此前版本判为「**用例的期望本身错误（关滤波器 ≠ 直通）**」，**该结论已撤回**。支撑它的判别实验，**两条读数都不能作证据**：① 判读样本用的是**裸 `i2c_read`**（本通路不稳），且**紧跟在一次失败事务之后**（按上面那条规律本来就该失败）；② 该实验的"旁路对照"步**构造有误**（发波方与引脚所有权不匹配 ⇒ 恒为 `-5`）。⇒ **「关滤波器 ≠ 直通」不是已证结论。** 处置方向不变，依据换成上面那条实测规律。
>
> ⚠️ 另：早期建议的"改用**旁路控制器**做对照"**不成立** —— 旁路控制器切换后**上游实例不在被测通路上**（拓扑错误），会产生假阴性。最终采用的是**同通路、单变量**的对照。

### 7.2 `i3c_i2c_switch_test / broadcast_nack_recovery` —— **用例时序竞态**

**测什么**：广播复位后，控制器在目标端的拒绝窗口内应收到一次「不确认」；目标端自动恢复后应能继续响应。

**失败点**：只有首帧。

**根因**：用例用**固定的 6 ms 延时**去抢目标端约 **6~8 ms** 的窗口。

**`PASS → FAIL` 精确钉在一个改动窗口上**：commit `43b232e`（2026-09-21 11:12）给该工程引入单出口改造，**同时在该用例的计时区间内**增加了三处操作（一次日志排空、一次 2 ms 延时、一次带 2000 ms 上限的等待）——**与 6~8 ms 的窗口同量级**。

**验证**：复跑 **3/3 全部失败，失败原因逐字相同** ⇒ **确定性失败，非偶发 flake**，支持时序竞态归因。

**结论：不得记为驱动回归。**

**建议**：把 6 ms 调整到 7~8 ms，或根治为**等待目标端状态信号**（去掉抢窗）。

### 7.3 `spi_test / link_probe` —— **外部回环跳线未接**

**测什么**：主从两设备双向 8 字节收发逐字节一致。

**现象**：主机侧返回 0，从机侧读到的是一个**哨兵初值**，且等待超时。

**归因**：从机侧的值是**用例自己的初值**，说明从机线程从未真正执行到写入点 —— 它等超时后被中止了。而**主机侧返回 0 并不证明"主机发得出去"**：SPI 主机的完成性与总线上有无对端无关。

原始串口里的关键形态：`timed_out=1`，MISO 读回全 `0xff`（空闲高），从机缓冲仍是初始化的 `0x00` —— **双向零流量，是"回路没接"的典型形态**。

**旁证**：同批次 `spid_test` 通过 10/10，而它需要的引脚与该用例需要的是**同一组**，**同批回归物理上不可能同时满足**。加上驱动文件在窗口内零改动、三份报告该行逐字相同 ⇒ **陈年，非回归**。

**需要的动作**：**物理接线**（4 线回环），且**必须先拆掉 `spid_test` 占用的同一组引脚跳线**——两者互斥。

> 另：该 case 报告里原先固定印着「接线：无」，那是**报告生成器里写死的模板文字**，对需要外部回环的用例不成立。**已修正为分列各套件的真实前置条件。**
