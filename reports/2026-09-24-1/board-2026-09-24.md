### 判读：`ctrl_fail_reason` 具体值

`CTRL:rstact_whole_should_nack` —— 来自 `ctrl_test_broadcast_nack_recovery()`：

```c
r1 = i3c_ccc_do_rstact_all(ctrl_i3c_dev, I3C_CCC_RSTACT_RESET_WHOLE_TARGET);
if (r1 == 0) {
        ctrl_set_fail("rstact_whole_should_nack");

```

即 **`r1 == 0`**：第一帧广播 RSTACT(whole) 返回**成功**，而测试期望它返回非 0（NACK）。

### 原始串口（CTRL，本轮 capture 轮，节选 broadcast 段）

```
I3C_I2C_TEST:CTRL:START:broadcast_nack_recovery
I3C_I2C_TEST:CTRL:FAIL:broadcast_nack_recovery:rstact_whole_should_nack

I3C_I2C_TEST:CTRL:SUMMARY:BEGIN
... （前 10 项均 PASS）
I3C_I2C_TEST:CTRL:SUMMARY:ITEM:broadcast_nack_recovery:FAIL:rstact_whole_should_nack

```

**关键否定证据**：整个 broadcast 段 CTRL 串口**没有任何驱动错误日志** ——
既无 `No response to broadcast address`，也无 `CCC[0x%02x] broadcast error, SER=0x%X`
（`zephyr/drivers/i3c/i3c_linkedsemi.c` 的广播分支只在 `EVR & ERRF` 时才置 `-EIO`）。
⇒ 控制器**硬件判定该帧正常收尾**（FCF 且无 ERRF），驱动按设计返回 0。
**不是"驱动把 NACK 吞了"，是"总线上确实被 ACK 了"或"该配置下广播无应答不产生 ERRF"。**

> ⚠️ **2026-09-24 二次更正**：上句"硬件判定该帧正常收尾"**只是同步窗口内的读数**，**不得**读成
> "硬件永不置 ERR"；同日一度提出的反向推论（"ANACK 晚 ~15ms 到位 ⇒ 驱动检查窗口过窄"）**也已
> 撤回**（其依据是 **deferred 日志的打印延迟**：本工程 `prj.conf:2` `CONFIG_LOG_MODE_DEFERRED=y`，
> 且该笔 `ret=0` 与通用路径 `return -EIO` 矛盾）。⇒ **两侧归因均无据，回"未定"**。
> 详细证据与真问题见 `KNOWN_ISSUES #98 增补 3` 二次更正批注 / `OPEN_ITEMS.md` O-39。

后续三帧（RSTACT peripheral / RSTDAA / EVR.BUSY 清零）**全部 PASS** ⇒ 总线自身工作正常。

### 证伪实验（决定性）

为区分"窗口位置不对"与"机制本身不成立"，做了一次**极端**对照（非"抢窗"式微调）：

- `NACK_WINDOW_MS` 10 → **500**（target 切 I2C 保持 500ms）
- controller 等待窗口 10ms → **250ms**（深插窗口内部，比任何 dispatcher 抖动量级大 40 倍）
- 窗口后等待 12 → 600ms

结果：**逐字相同的 FAIL**（`CTRL:rstact_whole_should_nack`，10/11）。
500ms 窗口 / 250ms 时刻仍拿到"被 ACK"，**时序推演被证伪** —— 这不是"到得太早/太晚"的问题。

### 退化机理（为什么是 10s，为什么是竞态）

`acquire.iwdg()` 的两遍烧录法：prime 轮 → `ctrl_cap.clear()` → capture 轮。

- **10s（首不安全）**：prime 轮的**最后一行**（`PROJECT EXECUTION SUCCESSFUL`）在 `clear()`
  **之后**才被采集线程收进缓冲 ⇒ 混进本轮归档。
  实测 CTRL 归档 71 行：**第 1 行是孤零零的 `PROJECT EXECUTION SUCCESSFUL`**（prime 轮尾巴），
  第 3 行才是本轮 boot banner；TGT 同理（23 行，尾部是 prime 轮的
  `TESTSUITE app_iwdg_domain succeeded` + `PROJECT EXECUTION SUCCESSFUL`，**缺了 ZT_BOOT 头**）。
  本轮 capture 的用例本体是**跑完的**（第 6~71 行是完整运行）。
- **8s（静默假 PASS）**：prime 轮被 taskkill 的时刻正好落在它刚打完收尾标记处 ⇒
  归档变成 `[prime 轮 64 行完整残片] + [本轮：boot banner、ZT_BOOT、1 行 START]`。
  实测 CTRL 70 行：第 1~64 行是 prime 轮的**整套逐项 PASS + TESTSUITE succeeded +
  PROJECT EXECUTION SUCCESSFUL**；第 66~71 行是本轮，**末行 = `START - test_feed_within_window_no_reset`**
  —— **本轮 capture 只跑到第 1 项就结束了**。
  然而报告是 **`PASS (18/18)`，`CTRL(cpu2)=SUCCESSFUL, TGT(cpu1)=SUCCESSFUL`** ——
  18 个 PASS 全部由 **prime 轮的残片**拼出，`PROJECT EXECUTION` 也来自残片。
  **被判定的是 prime 轮，不是 capture 轮；capture 轮根本没跑。这是货真价实的静默假 PASS。**

> ⇒ **本质**：下界由 `clear()` 与采集线程之间的**竞态**决定，**与判定逻辑无关**（判定在
> 所有档位输出完全相同）。所以"逐项一致"永远抓不到它，**只能查归档**。
> 又因为它是竞态，11s 只是"本次两轮都干净"，**贴边界取值不可靠** ⇒ 故取 30s。
